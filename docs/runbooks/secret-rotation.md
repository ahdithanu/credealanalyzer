# Secret rotation

Every secret here has a rotation path that does **not** interrupt users. That is
the point: a rotation that logs everyone out is a rotation that gets postponed,
which means it is the one you cannot perform under breach pressure.

## Session signing key

`SESSION_SIGNING_SECRET` signs CSRF tokens. Rotating it naively invalidates every
token in flight and every user's next save fails until they reload.

Use the dual-key window (`src/auth/session.js`, `csrfValid`):

```sh
# 1. Move the current key to the previous slot, generate a new current key.
aws secretsmanager put-secret-value --secret-id <SessionSecret> --secret-string \
  "{\"value\":\"$(openssl rand -base64 48)\",\"previous\":\"<the outgoing key>\"}"

# 2. Deploy. Tokens signed by either key now verify; new tokens use the new key.

# 3. Wait one full session lifetime (SESSION_TTL_MS, default 8h) so every token
#    signed under the old key has expired.

# 4. Clear the previous slot and deploy again.
```

Under active compromise, skip the window: rotate, deploy, and accept that every
user re-authenticates. **That is the correct trade when a key is known leaked** —
the window exists so routine rotation is painless, not so an emergency is gentle.

Minimum 32 bytes; `src/config.js` refuses to boot under that.

## Database credentials

The API holds **no** database password. `app_user` and `auth_user` authenticate
with short-lived IAM tokens minted per connection (`src/db/iamAuth.js`), so there
is nothing to rotate on the application side.

The **owner** credential (`cre_owner`) does exist, is generated by Secrets
Manager, and is used only by migrations and the operator CLIs. Enable automatic
rotation on it. It is the credential that bypasses every row level security
policy, so it is the one most worth rotating and least disruptive to rotate —
nothing long-lived holds it.

## WorkOS API key

1. Issue a second key in the WorkOS dashboard — both are valid at once.
2. Put the new value in Secrets Manager, deploy.
3. Confirm with `cd server && npm run sso:check`. It exchanges a deliberately
   invalid code and reports whether the credentials were accepted.
4. Revoke the old key in the dashboard.

Never rotate this without step 3. A wrong key fails at the moment a user signs
in, which is both the worst time to discover it and the hardest to attribute.

## SCIM tokens

Per tenant, stored only as a hash. Issue a replacement, update the directory's
configuration, confirm a sync, then revoke the old one. Both are valid in
between, so the customer's directory never reports a failed sync.

## Schedule

| Secret | Routine | Immediately when |
|---|---|---|
| Session signing key | 90 days | Suspected exposure; someone with access leaves |
| Owner DB credential | 90 days, automated | Same |
| WorkOS API key | 180 days | Same |
| SCIM tokens | 180 days | The customer asks, or their IT contact changes |

Rotation is only real if it has been performed once outside an incident. Put the
first one in the calendar.
